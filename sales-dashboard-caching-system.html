Sales Dashboard Caching System

How the Sales page serves its deals table from a daily-refreshed Supabase cache

The MAG Metrics dashboard's Sales page used to rebuild its deals table live on every load - querying Supabase and then making hundreds of ActiveCampaign API calls - which was slow and broke whenever ActiveCampaign was rate-limited or unavailable. It now reads a pre-computed Supabase cache that a scheduled job refreshes every weekday morning, so the page loads instantly and no longer depends on ActiveCampaign being reachable.

What changed

  • Before: every page load ran a Supabase query for around 260 deals, then fanned out to the ActiveCampaign API (owner lookup, custom-field metadata, per-deal custom fields and notes, plus bulk pagination). A cold load was slow and failed whenever ActiveCampaign was down.
  • After: the page reads a single Supabase cache table with one plain query. All the ActiveCampaign work now happens ahead of time, once a day.
  • The deals table also now stretches to the full width of the browser window instead of being capped - widen the window and the table grows with it.

How the data flows

Each weekday morning a scheduled job gathers the deal data from its two sources and writes one row per deal into the cache table:

Figure 1 - How the daily job fills the cache.

  • Supabase AC mirror - most of each row (created date, account, primary contact, reply status, deal status, demo date, proposal sent) comes from MAG's existing copy of the ActiveCampaign data already held in Supabase.
  • ActiveCampaign API - six columns live only in ActiveCampaign (lead type, job title, last note and its date, the owner's name, and whether a Magalog was sent). The job fetches these per deal.
  • The cache table - the job combines both into a single row per deal and saves it.

How the page reads it

With the cache in place, the Sales page no longer talks to ActiveCampaign at all. It simply reads the table:

Figure 2 - How the Sales page reads the cache.

Because it is a plain database read, the page loads almost instantly and keeps working even if ActiveCampaign is down. A short 10-minute server cache smooths out repeat visits.

The daily refresh

The refresh runs Monday to Friday at 6:00 am Philippine time. Each run does three things, and it never clears the table - it only adds new deals and updates existing ones:

1. Base refresh

Re-reads every in-scope deal from the Supabase mirror and updates the core columns for all of them.

2. Reconcile

If a deal has left scope (for example it was deleted or moved to another pipeline), its row is flagged as out-of-scope and hidden from the page - but the row is kept, never deleted.

3. Enrichment

Fills the six ActiveCampaign-only columns for new or recently changed deals. This runs in small batches with a time budget, so any backlog is worked through over successive mornings and then holds steady.

Scope: the LIV pipeline (Keynotes // Workshops // Immersive), deals created in 2026.

How it's built

Architecture

End to end, the system is a short pipeline:

  • Source data - MAG's Supabase database (a mirror of ActiveCampaign deals, accounts, contacts and custom fields) plus the live ActiveCampaign REST API for the six enriched columns.
  • sales-deals-sync - a Supabase Edge Function (Deno / TypeScript) that gathers the data and upserts it into the cache. It runs on a schedule and can also be triggered on demand.
  • Scheduler - a pg_cron job inside Supabase that calls the edge function each weekday at 6am PH time.
  • sales_liv_deals - the Supabase (PostgreSQL) cache table, one row per deal, keyed on the deal id.
  • Dashboard API - the Express endpoint /api/sales/deals reads the cache table and returns it to the browser.
  • Sales page - a plain HTML / CSS / JavaScript page that renders the rows as a sortable, searchable table.

Tech stack

  • Supabase (PostgreSQL) - data store and cache table
  • Supabase Edge Functions (Deno + TypeScript) - the daily sync job
  • pg_cron + pg_net - in-database scheduling that calls the function
  • ActiveCampaign REST API v3 - source of the enriched columns
  • Node.js + Express - the dashboard API
  • Plain HTML / CSS / JavaScript - the Sales page (no build step)
  • Google Cloud Run - hosting for the dashboard

What's stored in the cache

The cache table mirrors exactly the columns the deals table shows - one row per deal:

  • From the Supabase mirror: created date, account, primary contact, replied, status, demo date, proposal sent, owner id.
  • From ActiveCampaign: lead type, job title, last note (and date), owner name, Magalog sent.
  • Housekeeping (not shown on the page): a change-detection timestamp, an in-scope flag, and enrichment-progress markers.

On first set-up, all 258 current deals were populated and enriched with no errors.
