OVERVIEW
- Internal metrics dashboard for Sales / Marketing / Operations at My Adventure
  Group. Plain multi-page HTML app (one page per screen; tabs are links) with
  date-range + theme + chart/table toggles, behind a JWT login. No frontend
  build step.
- Sales and Operations are now LIVE, backed by real data queried at runtime
  from MAG's Supabase database. Marketing is partially live (leads, Google
  reviews, keynote/offsite booking counts+value) with several tiles still
  showing "needs setup" until their source is connected (see PENDING METRICS).
  Every metric/section in the API response carries a `meta.status` of "live",
  "partial", or "pending" plus a `source` label and, when pending, a `note`
  explaining what's needed — the frontend renders this as a source chip and a
  "needs setup" badge rather than faking a number.

SCRIPTS / APP CODE
- server/index.js — Express app: mounts /api routes, serves public/ as static
  files, / redirects to /sales_overview.html (the first tab). Generic metrics
  routes (/api/metrics/:area) are cached briefly per (area, range) via
  server/lib/cache.js. Dedicated sub-resource routers read pre-computed Supabase
  cache tables (plain SELECTs, 10-min cache): /api/sales/deals (LIV deals),
  /api/sales/topline (Sales top-line KPIs), /api/operations/buyer-sheet,
  /api/operations/invoice-tracking. Listens on $PORT (default 8080).
- server/auth.js / server/users.js — unchanged: JWT login, 3 bcrypt-hashed
  seed users (see README for demo credentials).
- server/config.js — reads every data-source credential from env vars
  (SUPABASE_DB_URL, AC_API_URL/AC_API_KEY, XERO_*, CALENDLY_TOKEN,
  MONDAY_TOKEN, GOOGLE_SERVICE_ACCOUNT_JSON/BUYER_ANALYSIS_SHEET_ID,
  GA4_ROUTINE_FIRE_URL/GA4_ROUTINE_FIRE_TOKEN) and exposes `hasSource(name)` so
  metric composers can degrade gracefully when a credential is absent.
- server/providers/supabase.js — pooled `pg` connection to the MAG Supabase
  Postgres database (SSL, rejectUnauthorized:false as required by Supabase's
  managed cert). This is the primary data source.
- server/lib/range.js — month-window date-range helper (3m/6m/12m/ytd →
  start date + a complete month-bucket axis) and `fillMonths` to left-join
  query results onto that axis so trends never have gaps.
- server/lib/sql.js — shared SQL fragments: SOURCE_BUCKET (buckets the
  free-text lead-source/program taxonomy MAG encodes in
  activecampaign_deals.title after "//", e.g. "Acme // Keynote") and
  LEAD_SOURCE_LABEL (friendly labels for leads.source_table).
- server/lib/metric.js — `live()/pending()/section()` wrappers giving every
  metric its consistent {value, unit, delta, meta} (or {data, meta} for
  sections) shape.
- server/metrics/{sales,marketing,operations}.js — compose the real Supabase
  queries (deals, leads, follow_up_sequence_logs, ac_custom_fields,
  google_reviews, activecampaign_contacts/accounts) into the API payloads;
  each returns a `notConfigured()` fallback (all metrics "pending") if
  SUPABASE_DB_URL isn't set, so the app never hard-fails on a missing
  credential.
- server/metrics/{liv-deals,mag-buyer-sheet,invoice-tracking,sales-topline}.js —
  sub-resource composers that each do a plain SELECT of a pre-computed Supabase
  cache table (no source calls at request time). sales-topline.js reads
  public.sales_topline for the Sales page: total_income (invoice_tracking, AUD,
  YTD + 12-mo trend), bureau (AC LIV pipeline group 3 / stage 113) and tailor
  (AC The Tailor pipeline group 7) are live; direct/indirect split, speaking
  enquiries and inbound/outbound stay "needs setup" until their AC fields/tags
  are mirrored to Supabase.
- public/ — plain static frontend, served directly (NO build step):
  - login.html + the tab pages (tab bar = links, in order): sales_overview.html
    ("Sales" top-line KPIs), marketing.html, operations.html, mag_buyer_sheet.html

    "Buyer Sheet"), invoice_tracking.html ("Invoices"), sales.html

    ("GA4 Agent" / on-demand report), ac_contact_sources.html
    ("GA4 & Ads Leads Tracking"), new_paid_leads_tracking.html
    ("New Paid Leads Tracking"), ac_ad_leads_tagging.html ("AC Ad Leads
    Tagging"), mag_sales_pulse.html ("MAG Sales Pulse").
  - ac_contact_sources.html is a wide, self-rendering table (reads
    /api/operations/contact-sources; does not use the generic chart helpers). As of

DATA MODEL / CAVEATS (important for anyone touching the queries)
- `activecampaign_deals.value` is stored in CENTS — always divide by 100.
  `currency` is mixed-case ("aud"/"AUD"/"usd"/...) — always lower() it.
- Deal value is CRM-contracted value, not billed revenue — Xero (not yet
  connected) is the source of truth for invoiced/billed amounts.
- Real demo/proposal signal is `ac_custom_fields.demo_date` /
  `.proposal_sent` — NOT `activecampaign_deals.demo_date_is_added` /
  `.proposal_sent_bool_is_added`, which are backfill-processed flags (true for
  every row) and meaningless as activity signals.
- `follow_up_sequence_logs` has only (id, created_at, lead_type, message_no) —
  no person identifier — so "people reached" cannot be derived from it; only
  send counts are computed.
- `leads.is_referred` is used as a rough direct/indirect proxy, but "bureau"
  is not an explicit tag anywhere in Supabase; treat that split as
  approximate (also true for the historical Direct/Indirect ratio in the
  Google "MAG BUYER ANALYSIS" sheet, ≈437:169, not yet wired in).
- Ignore `ac_deals_160726` / `ac_contacts_170726` (empty one-off backup
  snapshots) if exploring the schema further.

BUILD / RUN
- Dev: `npm install` (installs bcryptjs, express, jsonwebtoken, pg) then
  `npm run dev` (nodemon, :8080) or `npm start`. Without SUPABASE_DB_URL set,
  all metrics endpoints still respond 200 with every tile marked "pending" —
  useful for frontend-only work.
- No `npm run build` and no client install step.
- Container: single-stage Dockerfile (npm install --omit=dev; copy server/ +
  public/; run on Node 20 alpine).

DATA STORES (all in MAG's Supabase project aivitcomiywiysrfwqxt)
- Most metrics are read live from MAG's existing AC-mirror / leads / reviews
  tables. In addition, several dashboard-owned cache tables are filled on a
  schedule and only SELECTed at request time:
  - public.sales_liv_deals — LIV pipeline deal rows (Conferences page).
  - public.mag_buyer_sheet — Buyer Analysis rows (one per WON deal). As of
    2026-10-13 also carries engagement_fee numeric, amount_total numeric, and
    invoice_json text (migration 20261013010000). These come from
    public.invoice_tracking, matched by deal_title = ac_deal_title and SUMMED across
    a deal's invoices (deposit + final, up to 3): engagement_fee/amount_total are
    sums; invoice_json is a JSON ARRAY of the matched invoices' invoice_json objects
    (each with its `charges` breakdown). invoice_tracking is 2026+ only, so only ~31
    of 491 rows match. Filled deterministically in buyer-sheet-sync step 2a each run
    (null for deals with no 2026+ invoice). deal_title + deal_status (won/lost/open/
    removed, reconciled each run) are also now served to the page.
  - public.invoice_tracking — Xero sales invoices (Invoices page), keyed by
    invoice_id. As of 2026-10-13 also carries engagement_fee numeric(10,2),
    other_fees numeric(10,2), gst numeric, and invoice_json text. The fee split
    is by Xero account_code: engagement_fee = sum of line_amount_net for codes
    219–228 (MAG delivery/speaking revenue — keynote/immersive/program/workshop/
    teambuilding + virtual & Peak Teams variants); other_fees = sum of the rest
    (465 travel, 376 delivery expenses, merchandise, upsells). gst = invoice
    total tax (amount_tax). invoice_json = the whole Xero invoice object PLUS a
    computed `charges` breakdown {engagement_fee, other_fees, gst, net, total,
    lines:[{description, account_code, category, qty, unit_amount, net, tax,
    gross}]}. Identity: engagement+other = amount_net; engagement+other+gst =
    amount_total. These 4 columns are populated by the sync but NOT yet served
    by the API route / Invoices page.
  - public.sales_topline — Sales page top-line KPIs (long format
    metric/bucket/dimension/value/unit; RLS enabled). NEW this session.
  - public.dashboard_login_codes — bcrypt-hashed login OTP codes.
  - public.ga4_ac_contact_source — per-contact inferred acquisition source for
    the GA4 & Ads Leads Tracking page (/api/operations/contact-sources). PK =
    contact_id. As of 2026-10-09 it stores EVERY column the page shows, so the page
    reads it with no joins. Columns:
      * GA4/Calendly match columns (channel, source, medium, campaign, match_method,
        confidence, candidate_count, matched_at, time_delta_seconds) — filled by the
        rebuild (section 1).
      * deal_id — linked by the rebuild (section 1b).
      * conversion_action, conversion_link, deal_title, deal_value, deal_status,
        source_type, cpc — DENORMALIZED each rebuild (section 3), mirroring the
        joins the page query used to do (ga4_ac_event_matches, activecampaign_deals
        +ac_deal_source_type, conversion_events_ac_matched).
      * google_ads_ac_field / deal_source_ac_field — filled by
        ga4-ac-custom-fields-sync after the rebuild.
    The rebuild (section 4) also appends/UPSERTS the primary contact of each
    ac_google_ads_deals deal (GA4/match columns left NULL; deal_*/source_type/
    google_ads_ac_field from the AC deal data — deal_value already AUD; cdate from
    activecampaign_contacts). It reads the prior run's ac_google_ads_deals snapshot
    (~1-day lag for brand-new Google-Ads leads).
    As of 2026-10-13 this table ACCUMULATES (was truncate+rebuilt each run): the
    rebuild UPSERTs on contact_id and never truncates, so contacts older than the
    60-day match window are RETAINED on the page (forward-looking — rows truncated
    away before 2026-10-13 are gone). Ownership split to avoid the AUD/cents bug now
    that gads rows persist: MATCHED rows (match_method NOT NULL) are owned by
    sections 1/1b/3 (deal_value = activecampaign_deals.value/100); GOOGLE-ADS rows
    (match_method NULL, deal_value AUD) are owned solely by section 4's upsert, and
    sections 1b/3 are scoped to match_method IS NOT NULL so they never touch them.
    Deal fields on matched rows refresh every run (so edits to the AC deal flow
    through); gads rows refresh from ac_google_ads_deals every run.
  - public.ac_google_ads_deals — all AC deals whose "Google Ads?" custom field =
    "Yes", with deal/contact/account metadata. PK = deal_id. Filled by the
    ac-google-ads-deals-sync edge function.
  - public.ga4_ac_event_matches — per-event audit log (one row per GA4 form event
    / Calendly booking, with its best-matched contact) backing the rebuild's
    conversion_action/conversion_link denormalization. As of 2026-10-13 this is an
    ACCUMULATING table (was truncate+rebuilt): rebuild_ga4_ac_matches() section 2
    UPSERTs on event_uid (a deterministic md5 of the event DIMENSIONS — event_kind,
    event_time rendered in UTC, event_name, source, medium, campaign,
    conversion_link — plus an occurrence tiebreaker; event_count is EXCLUDED since
    it's a revisable measure). Rows that age out of the staging window are NO LONGER
    deleted, so event history is retained beyond 60 days (forward-looking only —
    history truncated away before 2026-10-13 is gone). event_uid is NOT NULL + unique;
    inserted_at = first-seen, last_rebuilt_at = last re-derivation.
- Login is passwordless email OTP (codes stored in dashboard_login_codes); the
  old seeded-user array is no longer the auth path.

AUTOMATIONS / ROUTINES
- sales-topline-sync (Claude cloud routine, trig_011z2MX6Sh5gsBY6JncmDmss) —
  runs weekly, Mon 06:00 Asia/Manila (cron `0 22 * * 0` UTC), via the Supabase
  MCP connector. Recomputes public.sales_topline (idempotent UPSERTs over a
  rolling 12-month window) from invoice_tracking + activecampaign_deals. SQL is
  documented in routines/sales-topline-sync.md. NEW this session.
- The sales_liv_deals / mag_buyer_sheet cache tables are refreshed Mon–Fri 6am PH
  by Supabase Edge Functions (sales-deals-sync, buyer-sheet-sync); invoice_tracking
  is refreshed by a separate scheduled Claude routine from Xero. buyer-sheet-sync
  (pg_cron jobid 6, '0 22 * * 0-4', deployed verify_jwt:false) was redeployed to
  VERSION 12 on 2026-10-13: a new base step 2a looks up public.invoice_tracking by
  ac_deal_title and writes the aggregated engagement_fee/amount_total/invoice_json
  onto each row every run (see the mag_buyer_sheet DATA STORES entry).
- invoice-tracking-sync (Claude cloud routine, trig_013TGsR7euBvPbAz45UpS8tb) —
  cron `0 22 * * 0-4` (Mon–Fri 6am PH), model sonnet, via the Xero + Supabase MCP
  connectors (Xero read-only). Its deterministic transform.mjs is embedded in the
  routine PROMPT (edit it there, not in the repo): pages through 2026+ ACCREC
  invoices, upserts public.invoice_tracking keyed on invoice_id (never truncates),
  then matches each invoice to the best AC deal (ac_deal_title). As of 2026-10-13
  it also fills engagement_fee/other_fees/gst (split by Xero account_code; see the
  invoice_tracking DATA STORES entry) and an invoice_json enriched with a computed
  `charges` breakdown. Xero access is the ACCOUNT'S Xero MCP connector — no Xero
  token stored anywhere (not Supabase/Secret Manager/repo); if that connector's
  auth lapses the run fails until reconnected.
- GA4 & Ads Leads Tracking daily chain — as of 2026-10-09 driven by ONE cron job
  and ONE orchestrator edge function (was 3 staggered jobs). pg_cron job
  `contact-sources-sync-daily` ('0 22 * * *' = 06:00 PH daily) POSTs the
  contact-sources-sync edge function (bare → 202 + background). That orchestrator:
  (a) FIRES ac-google-ads-deals-sync async (fire-and-forget, ~138s, runs in its own
  worker — it's independent: the rebuild doesn't read ac_google_ads_deals and the
  page doesn't join it); then (b) AWAITS, in order, ga4-ads-leads-sync?sync=1 (the
  rebuild_ga4_ac_matches RPC: rebuild ga4_ac_contact_source + ga4_ac_event_matches,
  link deal_id, denormalize display columns, append Google-Ads leads) then
  ga4-ac-custom-fields-sync?sync=1 (fills google_ads_ac_field/deal_source_ac_field
  on the rebuilt rows). Awaiting just the ordered pair is ~52s — awaiting all three
  blew the ~150s edge worker limit (HTTP 546), which is why step 1 is fire-and-forget.
  The 3 original edge functions are KEPT and still individually callable (?sync=1);
  only their individual cron jobs were removed — the superseded schedule files in
  supabase/ are marked SUPERSEDED. GOTCHA (still applies): every edge function here
  MUST be deployed --no-verify-jwt — the crons/orchestrator send no Authorization
  header, so with verify_jwt=true the gateway 401s before the body runs while pg_cron
  still shows "succeeded". New schedule SQL:
  supabase/migrations/20261009000100_schedule_contact_sources_sync.sql.
- update-deals-daily-7am-pht (pg_cron, '0 23 * * *' = 07:00 PH daily) — runs
  public.update_ga4_contact_deals(), a lightweight SECOND deal-linker that runs an
  hour after the 06:00 rebuild (by then the activecampaign_deals mirror, refreshed
  by sales-deals-sync at the same 06:00 slot, is settled). It re-links deal_id on
  ga4_ac_contact_source rows with the same primary/org-match logic as rebuild step
  1b. As of 2026-10-13 it ALSO denormalizes deal_title/deal_value/deal_status/
  source_type (mirrors rebuild step 3b, scoped to match_method IS NOT NULL so the
  Google-Ads-appended rows — deal_value already in AUD — aren't clobbered). This
  closed the bug where org-matched non-primary contacts had deal_id but a blank
  deal_title. Migrations this session:
  supabase/migrations/20261013000000_denormalize_deal_cols_in_update_ga4_contact_deals.sql
  and 20261013000100_ga4_ac_event_matches_accumulate_no_truncate.sql.
- MAG's own lead-gen/outreach automations (LinkedIn scraping, cold-lead
  sequencing, proposal routing) write into the Supabase tables this dashboard
  reads; they are external to this repo.
