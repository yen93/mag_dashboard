--------------------------------------------------------------------------------
ASSISTANT:
Investigated read-only and answered: there is NO cache table for the ROAS tab — it
is computed LIVE at request time. Evidence:
  • `server/metrics/roas.js` GROUPs the VIEW `public.roas_counted_deals` by FY and
    joins the monthly spend tables; header comment confirms "LIVE, computed at
    request time ... NOT a cache".
  • `server/index.js:262` wraps getRoas in `cached('operations:roas', getRoas,
    10*60*1000)` — a ~10-min in-memory response cache (same for /roas/deals and
    /contact-sources/roas-counted).
  • Confirmed via Supabase information_schema (project aivitcomiywiysrfwqxt) that
    `roas_counted_deals` is a VIEW and the sources (bing/clover/ga4/google/niki/
    simple_digital + ga4_ac_contact_source) are BASE TABLEs.
Explained the two freshness layers (10-min response cache; base tables filled by
scheduled syncs) and that a new conversion does NOT appear instantly — it shows
after the next daily/weekly sync (usually next day), and FY25+ deals must be
attributed to paid search (Google Ads=Yes / JC tag / GA4 cpc) to be counted.
Gave the source→cadence table (AC deals daily ~5am PH; GA4 leads daily ~6am PH;
clover audit + Niki's log static; Google Ads weekly Mon ~6am; Bing+SD weekly Mon
~6:30am via Xero). No changes made (/q).
