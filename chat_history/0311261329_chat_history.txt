ASSISTANT:
Root-caused the clipping. Inspected .kpi CSS in roi.html (lines 77-96) and app.css.
Finding: commit 272eb9f ("match ROI tab look and feel to ROAS") added a hover-lift
`transform: translateY(-3px)` to `.kpi`. A transform makes the card its own
stacking context, which TRAPS the tooltip's z-index:60 inside the card. Because the
card itself has no z-index (auto/0) and all .kpi cards are position:relative, the
whole hovered card — tooltip included — paints BELOW the sticky toolbar
(z-index:9). So a top-row KPI card's upward-opening ⓘ tooltip is painted under the
toolbar and cut off. Same clipping class as the heading tooltip fixed earlier in
112cfaa (opened downward then) — reintroduced on the cards by the hover-lift, hence
"broken again".

Fix (public/roi.html, after the .kpi:hover rule ~line 88): added

    .kpi:hover, .kpi:focus-within { z-index: 40; }

Since .kpi is already position:relative, this lifts the hovered/focused card's
whole subtree (tooltip included) above the toolbar (z-9) and sibling cards, so the
tooltip escapes. Covers mouse hover and keyboard focus (:focus-within); keeps the
tooltip opening upward like every other source icon on the page. Considered
flipping the KPI tooltip downward (the heading's approach) but rejected it: all
cards are position:relative with no z-index, so a downward tooltip would instead be
clipped by the row below — the z-index lift is needed either way, so the minimal
upward-preserving fix is cleanest.

Noted it's frontend-only (no app.js touched → no ?v= bump) and needs a MANUAL
Cloud Run redeploy (per CLAUDE.md, Claude never deploys). Offered a follow-up to
harden the shared .src-tip once in app.css so this stops recurring per-page; left
it page-local pending the user's call.
