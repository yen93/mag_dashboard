(Q, no action) Is it better for ga4_ac_event_matches to be upserted instead of
truncated?

--------------------------------------------------------------------------------
ASSISTANT:
Reasoned it through specific to that table: truncate-and-rebuild is the better fit
AS LONG AS you don't need history — it's a pure derived projection with no clean
natural key, global recompute semantics (truncate handles removals for free), and
it's tiny/daily. The single transaction means readers never see it empty. Listed
the conditions under which upsert would win (stable id referenced elsewhere;
expensive full rebuild; need to retain rows beyond the window).

ASSISTANT:
Implemented and verified Option A.

Discovery first: inspected ga4_ac_event_matches + staging schemas. Table has
id (GENERATED ALWAYS AS IDENTITY) and inserted_at (default now()); neither
staging source (ga4_events_staging, calendly_bookings_staging) has a stable
event id, so a key had to be synthesized. Checked for duplicate natural-dim
groups — found 0 everywhere, both with and without event_count. Confirmed
activecampaign_contacts.id is text (UNION type-compat for matched_contact_id).

Design: event_uid = md5 of event DIMENSIONS (event_kind, event_time rendered as
UTC via to_char(... at time zone 'UTC', 'YYYY-MM-DD HH24:MI:SS.US') so it's
timezone-independent, event_name, source, medium, campaign, conversion_link) +
an occurrence tiebreaker (row_number over those dims). event_count is EXCLUDED
from the key (it's a measure that GA4 can revise; including it would duplicate
instead of update). Added columns event_uid (NOT NULL, unique index) and
last_rebuilt_at; inserted_at now serves as first-seen.

Rebuild change: section 2 of rebuild_ga4_ac_matches() no longer truncates — it
builds GA4 + Calendly rows in CTEs, computes event_uid, and does
INSERT ... ON CONFLICT (event_uid) DO UPDATE (refreshing mutable fields +
last_rebuilt_at). Rows that age out of staging simply stay, so history accrues.
Return JSON now reports event_audit_upserted + event_audit_retained_total.

Applied via MCP migration `ga4_ac_event_matches_accumulate_no_truncate`; mirrored
to repo file
supabase/migrations/20261013000100_ga4_ac_event_matches_accumulate_no_truncate.sql.

Verified: backfill produced 792 rows, 0 null / 0 duplicate event_uid; ran the
rebuild live → event_audit_upserted=792, event_audit_retained_total=792 (every
current event matched its key and updated in place — zero duplication, zero loss,
no errors); events already span back to 2026-08-13. Noted two honest points:
retention is forward-looking (history already truncated away in past runs can't be
recovered), and ga4_ac_contact_source was intentionally left on truncate-rebuild
(it's a current-state working view, not an event log).
