ASSISTANT:
Read public/ac_contact_sources.html and server/metrics/ac-contact-sources.js.
The two columns map to cs.google_ads_ac_field ("Google Ads (AC)") and
cs.deal_source_ac_field ("Deal Source") on public.ga4_ac_contact_source. Those
are populated only by the edge function ga4-ac-custom-fields-sync (NOT
ac-google-ads-deals-sync, which writes a different table, ac_google_ads_deals).

Read both new edge functions:
- supabase/functions/ga4-ac-custom-fields-sync/index.ts — resolves AC deal
  custom-field IDs ("Google Ads?"=18, "Deal Source?"=6), fetches per-deal custom
  fields, and UPDATEs ga4_ac_contact_source by deal_id.
- supabase/functions/ac-google-ads-deals-sync/index.ts — scans AC for deals with
  "Google Ads?"=Yes and upserts ac_google_ads_deals.

A background agent found the Supabase project ref (aivitcomiywiysrfwqxt,
MAGTestProject) and the cron schedules: ga4-ads-leads-sync rebuilds the table at
06:00 PHT (22:00 UTC); update_ga4_contact_deals links deal_id at 07:00 PHT;
ga4-ac-custom-fields-sync runs at 07:10 PHT (23:10 UTC).

Investigated the live DB via Supabase MCP:
- ga4_ac_contact_source: 71 rows, 15 with deal_id, but 0 with google_ads_ac_field
  / deal_source_ac_field. max(updated_at) was 22:00 UTC (the table rebuild), i.e.
  the 23:10 custom-fields-sync had not touched a single row.
- list_edge_functions showed ga4-ac-custom-fields-sync AND ac-google-ads-deals-sync
  both had verify_jwt=true, unlike every sibling function (ga4-ads-leads-sync,
  calendly-source-sync, new-paid-leads-sync are all verify_jwt=false).
- cron.job_run_details: ga4-ac-custom-fields-sync-daily had never run (null
  status); the others "succeeded" — but that only means pg_net queued the POST.
- Read supabase/schedule_ga4_ac_custom_fields_sync.sql: the cron sends only
  Content-Type, no Authorization header.
- net._http_response id 50 (the 21:30 deals-sync run) returned
  401 {"code":"UNAUTHORIZED_NO_AUTH_HEADER","message":"Missing authorization
  header"} — proving the edge gateway rejects the no-auth cron POST before the
  function body runs.

ROOT CAUSE: both functions deployed with verify_jwt=true (default), while their
crons post with no Authorization header → 401 → sync never executes → the two
columns stay NULL → blank in the UI. Nothing wrong with the SQL, schema, or
function logic. Each function's own header comment even says deploy
--no-verify-jwt; it wasn't.

Attempted the fix via Supabase MCP deploy_edge_function (verify_jwt=false) but it
was denied by the auto-mode classifier as a Production Deploy. Stopped and
explained the diagnosis, then asked (AskUserQuestion) how to apply it. User chose
"Approve MCP redeploy."

ASSISTANT:
Added a display-only filter to isExcludedRow() in public/ac_contact_sources.html
(frontend only — the server still returns the rows; data untouched in DB):

  var ga = String(r.googleAdsAcField || '').trim().toLowerCase();
  var hasConv = r.conversionAction !== null && r.conversionAction !== undefined
                && String(r.conversionAction).trim() !== '';
  if (ga === 'no' && !hasConv) return true;

Explained that it only hides rows where BOTH conditions hold, and that because
the page routes all rows through isExcludedRow, the rows drop from both the table
and the KPI counts (consistent with the existing referral/teams/email exclusions).
Takes effect on page refresh (no build step). Offered to mirror the rule
server-side in server/metrics/ac-contact-sources.js.
