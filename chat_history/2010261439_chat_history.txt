Traced where the FY value comes from:
  - Read supabase/migrations/20261020060000_contact_source_fy_calyr_jc_columns.sql.
    The fy column on public.ga4_ac_contact_source is GENERATED ALWAYS AS
    (public.mag_fy_label(cdate)) STORED. mag_fy_label() emitted
    'FY' || fy_start::text || '-' || right((fy_start+1)::text, 2) → "FY2026-27",
    where fy_start is the AU FY start year (Jul 1 boundary, computed in UTC).
  - Grepped the server + page: server/metrics/ac-contact-sources.js just SELECTs
    cs.fy AS "fy"; public/ac_contact_sources.html renders it as plain text
    ({ key:'fy', label:'FY', render: txt }). No format parsing anywhere, so a pure
    DB change suffices.

Key subtlety: a GENERATED STORED column is only recomputed on INSERT/UPDATE of a
row. CREATE OR REPLACE FUNCTION alone would NOT rewrite already-stored values
(static roas-* and out-of-window rows would keep "FY2026-27"). So the migration
drops the generated column, replaces the helper, then re-adds the column — re-adding
recomputes it for every existing row.

Wrote supabase/migrations/20261020080000_contact_source_fy_short_label.sql:
  1. alter table ... drop column if exists fy;
  2. create or replace function public.mag_fy_label(ts) → new body:
     'FY' || right(fy_start::text, 2)  (e.g. fy_start 2026 → "FY26").
  3. alter table ... add column if not exists fy text
       generated always as (public.mag_fy_label(cdate)) stored;

Applied it live via Supabase MCP apply_migration to project aivitcomiywiysrfwqxt
